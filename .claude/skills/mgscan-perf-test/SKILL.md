# Management Scan Performance & Functional Test

Full methodology lives in `docs/management-scan-testing-runbook.md` — **read it before running
anything**, it documents every selector gotcha discovered building this (Knockout `visible` vs
`if` hiding stale buttons, the duplicated `commonFilter` mount under both tabs, the
`onSave`/`onSavePassword` substring collision, etc.). This file is the short trigger + sequencing
reference; the runbook is the source of truth for *why* each step is shaped the way it is.

Baseline numbers from the first full pass: `docs/management-scan-baseline-2026-08-10.md`. Every
run since is accumulated in `results/mgscan-perf-trend.json` (see runbook §9) — this is the
durable cross-release record, not any single dated comparison doc.

## When invoked

1. **Confirm scope with the user first** if it's not already clear from their request:
   - Fresh full run (new hierarchy + new assessment cycle), or reuse an existing `runStamp`'s
     accounts/results from a prior run (check `results/account-setup-*.json` for what exists)?
   - Compare against the immediately prior run, the original baseline, or just produce a
     standalone report?
2. Do **not** create new test accounts/data without the user's go-ahead first — this repo's
   working convention (see `docs/management-scan-account-setup-plan.md`) is plan-before-create
   for anything that touches the shared IT environment, even though it's fresh/throwaway data.
3. **Before running the full suite, confirm what's actually deployed** — runbook §9's
   "functional fingerprint" check. If the user says this run is meant to test a specific new
   release, identify one behavior that release changed and verify it live (e.g. a question
   count, a new button, a changed label) *before* spending time on the full timing sweep. Finding
   out afterward that the environment wasn't actually updated (as happened 2026-08-12) wastes the
   whole run as a release comparison, even though it's still valid as a stability check.
4. Run the runbook's steps **in order** (§2 → §7) — each depends on the previous step's output
   file (`results/account-setup-<runStamp>.json` feeds every later script).

## Quick command sequence (see runbook for full detail/gotchas on each)

```bash
CREDS_FILE=.credentials.local.json node create-mgscan-test-accounts.mjs <runStamp>
node complete-mgscan-assessments.mjs <runStamp>
node director-publish.mjs <runStamp> manager      # NOT director — see runbook §4, real bug if you use director
node measure-mgscan-full.mjs <runStamp> employee mgscan-full <runTs>
node measure-mgscan-full.mjs <runStamp> manager  mgscan-full <runTs>
node measure-mgscan-full.mjs <runStamp> director mgscan-full <runTs>
node create-mgscan-test-accounts.mjs <runStamp2> validation-only
node assign-manager.mjs "ValidationCheck" "Director"
node test-assessment-validation.mjs <runStamp2>
node build-final-report-data.mjs <employeeFile> <managerFile> <directorFile> <validationFile> <combinedFile>
node generate-excel-perf.mjs "results/<combinedFile>" "reports/ManagementScan_FULL_Report.xlsx"

# then record this run into the cross-release trend log (write results/release-<runStamp>.json first — see runbook §9):
node record-perf-run.mjs <combinedFile> <runStamp> <date> results/release-<runStamp>.json
node compare-perf-runs.mjs > docs/management-scan-perf-comparison-latest.md
```

## After running

1. Open the generated report's **Known Issues** sheet and diff it against the prior run's —
   call out explicitly which issues are still present, which are fixed, and any genuinely new
   ones. Don't silently re-report a known issue as if it were new.
2. Read `docs/management-scan-perf-comparison-latest.md` (auto-generated by
   `compare-perf-runs.mjs`) for the timing diff — don't hand-transcribe numbers into a new doc,
   that's what produced the "same release" detection bug this process fixed. Only write a short
   dated narrative doc for things the script can't know: bug re-verification, new functional
   observations, next steps.
3. If the comparison script's release-identity banner says both runs share a `releaseId`, say so
   plainly in your report to the user — a stability check and a release comparison answer
   different questions and shouldn't be presented as the same thing.
4. Report results with Manager and Director kept in **separate** sections/rows, never merged —
   this was an explicit requirement the first time and should stay the default going forward.
5. Update the project dashboard's Performance section (if one exists for this project) from the
   comparison output, not from memory of the numbers.
6. **Git:** this repo's `main` is shared — do this work on a personal branch (e.g.
   `<name>/mgscan-perf-testing`) and do not push to `main` or any other branch without the user
   explicitly asking. Confirm before pushing anywhere.
